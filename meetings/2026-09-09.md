## Discussion

### 1. SIG Charter And Responsibilities

What needs to be decided:
Define whether the SIG is mainly a discussion forum, a recommendation body, or an approval gate for Rust-related work in RDK-B, and which responsibilities belong in the initial operating model.

Options:

- Option A: advisory forum only, focused on discussion and knowledge sharing.
- Option B: advisory and recommendation body, responsible for guidance, proposal review, and reusable patterns.
- Option C: formal approval gate for Rust architecture decisions across RDK-B.

Final SIG decision:
Option B moving into C to push rules in the future.

### 2. Membership And Participation

What needs to be decided:
Define who can participate, whether there is a formal member list, and how active contributors are recognized for decisions and follow-up work.

Options:

- Option A: open participation for anyone interested in Rust in RDK-B, with no formal membership.
- Option B: open participation with an informal active-contributor group based on recent attendance or repository activity.
- Option C: fixed membership with named company representatives.

Final SIG decision:
 option A and B, action point for Danny to get a list of people interested, contact companies like Airties, MXL, Cujo, consult read.

### 3. Chair, Co-Chair, And Maintainer Roles

What needs to be decided:
Define whether the SIG needs named meeting leads, repository maintainers, backup coverage for agenda preparation and decision tracking, and a documented process for role transitions.

Options:

- Option A: one chair only, with repository changes handled ad hoc.
- Option B: chair and co-chair for meeting leadership, plus one or more repository maintainers.
- Option C: maintainer-only model with rotating meeting facilitator.

Final SIG decision:
Approved. Justin serves as chair, Jose serves as co-chair, and Danny serves as technical project manager for the initial operating period and I propose Elaine as participant in the maintainers group next to us.

### 4. Meeting Cadence

What needs to be decided:
Define how often the SIG meets, whether the cadence should be fixed or adjusted after the SIG becomes established, whether special topic meetings should be separate from the regular cadence, and whether participants must state or display their affiliation and GitHub ID during SIG calls using the format `[affiliation] @github-id` or `[affiliation] name`.

Options:

- Option A: monthly 60-minute meeting.
- Option B: biweekly 60-minute meeting for the first quarter, then review the cadence.
- Option C: ad hoc meetings only when proposals are ready.

Final SIG decision:
Biweekly if no content we cancel, we can review next year.

### 5. Agenda Preparation

What needs to be decided:
Define who prepares the agenda, when it is published, and how contributors can add or prioritize topics.

Options:

- Option A: chair publishes the agenda before each meeting.
- Option B: chair or co-chair publishes a draft agenda at least five business days ahead, with community additions until two business days before the meeting.
- Option C: agenda is built live at the start of the meeting.

Final SIG decision:
Option B, reminding  community to add points via Slack or proposal flow.

### 6. Decision-Making Process

What needs to be decided:
Define how the SIG records agreement, what happens when there is disagreement, whether asynchronous decisions in GitHub are allowed, whether the `rust-sig-maintainers` GitHub group may approve Pull Requests based on documented SIG consensus, whether any decision classes require a stronger approval rule, and how active contributors are counted for a fallback vote.

Options:

- Option A: decisions only in live meetings by attendees present.
- Option B: rough consensus in meetings or Pull Requests, with the recorded outcome becoming effective when documented and Pull Requests approved by members of the `rust-sig-maintainers` GitHub group based on SIG consensus.
- Option C: formal votes for all decisions.

Final SIG decision:

Mix a B and C, depending on how important is the decision, add agenda straw ballot sessions.

### 7. Meeting Minutes And Action Tracking

What needs to be decided:
Define how minutes are written, when they must be published, and how action items are assigned and tracked.

Options:

- Option A: summary minutes only, with action items tracked informally.
- Option B: concise minutes stored in `meetings/`, with action items recorded using an owner, target date, and status.
- Option C: external tracker for actions like Wiki, with only a short meeting summary in the repository.

Final SIG decision:
Format minutes to be properly tracked in GIT.

### 8. Technical Proposal Process

What needs to be decided:
Define when a topic requires a proposal, what minimum content a proposal must include, how proposals move from draft to accepted guidance, whether proposals are the trigger documents for new technical projects to be discussed in meetings and for starting task-force groups, whether live meeting review is required, and whether proposal approval requires explicit maintainer sign-off in addition to recorded SIG consensus.

Options:

- Option A: proposals only for large architectural changes.
- Option B: proposals for any topic that introduces shared guidance, reusable infrastructure, cross-team architectural impact, or a new technical project requiring SIG discussion, with proposals also serving as trigger documents for starting task-force groups and approval based on recorded SIG consensus and maintainer sign-off when required.
- Option C: proposals for all technical topics.

Final SIG decision:
Option B, with a good technical proposal, we prepare the template for new proposals.

### 9. Task-Force Creation And Ownership

What needs to be decided:
Define when a task force should be created, whether it may be triggered by a SIG proposal used as the trigger document or by existing component-stack work, whether it may be used to request reserved capacity from RDKM or any other contributor, whether it should be managed through an ad hoc GitHub Project, what ownership it needs, whether task-force owners must also be repository maintainers, and how inactive task forces are closed or merged back into general SIG work.

Options:

- Option A: create task forces informally whenever volunteers exist or new topics are raised.
- Option B: create a task force when triggered by a SIG proposal or existing component-stack work, use it to document resource needs and request reserved capacity from RDKM or any other contributor where needed, manage the work through a GitHub Project created ad hoc for the SIG task-force group, require a named owner, scope, expected deliverable, and review date, and decide separately whether task-force owners must also be repository maintainers.
- Option C: avoid task forces and keep all work in the main SIG.

Final SIG decision:
We need a task force template.

### 10. Communication Workflow For Mail Or Slack, Issues, And Pull Requests

What needs to be decided:
Define whether to use mail or Slack for exploratory topics and agenda input, Issues for action items, Pull Requests for document changes and proposal approval, whether GitHub Discussions should be enabled, and whether labels or templates are needed for SIG work.

Options:

- Option A: use Issues for everything.
- Option B: use mail or Slack for exploratory topics and agenda input, Issues for action items and tracked work, and Pull Requests for document changes and proposal approval.
- Option C: rely mainly on meetings, using Pull Requests only for final text.

Final SIG decision:

Option B, email secondary

### 11. Full CI Guideline Approval

What needs to be decided:
Define whether the SIG should approve `guidelines/ci.md` as the full CI guideline for Rust component repositories, including the documented use of `cargo fmt --check`, `cargo clippy`, `cargo test`, `cargo audit`, `cargo deny`, `cargo hack`, and `cargo llvm-cov`.

Options:

- Option A: approve only a basic recommendation and keep the broader CI tooling guidance proposed.
- Option B: approve the full CI guideline, with `cargo fmt --check`, `cargo clippy`, `cargo test`, and `cargo audit` as the minimum checks, and `cargo deny`, `cargo hack`, and `cargo llvm-cov` as recommended optional checks based on repository risk and CI budget.
- Option C: keep the full CI guideline proposed until new components are added to the stack.
- Option D: keep the full CI guideline until we decide the task force is accomplished.
