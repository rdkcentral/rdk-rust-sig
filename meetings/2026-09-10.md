## Discussion

### 1. SIG Charter And Responsibilities

What needs to be decided:
Define whether the SIG is mainly a discussion forum, a recommendation body, or an approval gate for Rust-related work in RDK-B.

Options:

- Option A: advisory forum only, focused on discussion and knowledge sharing.
- Option B: advisory and recommendation body, responsible for guidance, proposal review, and reusable patterns.
- Option C: formal approval gate for Rust architecture decisions across RDK-B.

Recommended default:
Option B. The SIG should publish guidance, review proposals, and coordinate shared direction without becoming a mandatory approval gate for every Rust change.

### 2. Membership And Participation

What needs to be decided:
Define who can participate, whether there is a formal member list, and how active contributors are recognized for decisions and follow-up work.

Options:

- Option A: open participation for anyone interested in Rust in RDK-B, with no formal membership.
- Option B: open participation with an informal active-contributor group based on recent attendance or repository activity.
- Option C: fixed membership with named company representatives.

Recommended default:
Option B. Keep meetings open, but maintain an informal active-contributor set for ownership, reviews, and quorum-sensitive decisions.

### 3. Chair, Co-Chair, And Maintainer Roles

What needs to be decided:
Define whether the SIG needs named meeting leads, repository maintainers, and backup coverage for agenda preparation and decision tracking.

Options:

- Option A: one chair only, with repository changes handled ad hoc.
- Option B: chair and co-chair for meeting leadership, plus one or more repository maintainers.
- Option C: maintainer-only model with rotating meeting facilitator.

Recommended default:
Option B. Use a chair and co-chair for continuity, and keep repository maintenance explicit so agendas, minutes, and proposals do not become orphaned.

### 4. Meeting Cadence

What needs to be decided:
Define how often the SIG meets and whether the cadence should be fixed or adjusted after the SIG becomes established.

Options:

- Option A: monthly 60-minute meeting.
- Option B: biweekly 60-minute meeting for the first quarter, then review the cadence.
- Option C: ad hoc meetings only when proposals are ready.

Recommended default:
Option B. A biweekly cadence creates enough momentum to establish process and initial work items, while still allowing a later adjustment based on participation.

Options:

- Option A: chair publishes the agenda before each meeting.
- Option B: chair or co-chair publishes a draft agenda at least five business days ahead, with community additions until two business days before the meeting.
- Option C: agenda is built live at the start of the meeting.

Option B. A short lead time keeps meetings efficient while still allowing open topic submission.

### 6. Decision-Making Process

What needs to be decided:
Define how the SIG records agreement, what happens when there is disagreement, and whether asynchronous decisions in GitHub are allowed.

Options:

- Option A: decisions only in live meetings by attendees present.
- Option B: rough consensus in meetings or Pull Requests, with the recorded outcome becoming effective when documented.
- Option C: formal votes for all decisions.

Recommended default:
Option B. Prefer rough consensus and documented rationale, using a simple vote only when consensus cannot be reached in a reasonable time.

What needs to be decided:
Define how minutes are written, when they must be published, and how action items are assigned and tracked.

Options:

- Option A: summary minutes only, with action items tracked informally.
- Option B: concise minutes stored in `meetings/`, with action items recorded using an owner, target date, and status.
- Option C: external tracker for actions, with only a short meeting summary in the repository.

Recommended default:
Option B. Keeping minutes and actions in the repository preserves traceability between discussion, decisions, and follow-up work.

What needs to be decided:
Define which repository workflows should be used for open-ended discussion, action tracking, and approval of repository changes.

Options:

- Option A: use Issues for everything.
